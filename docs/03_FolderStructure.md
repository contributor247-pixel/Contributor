## Reasoning per top-level folder

- **`drizzle/schema/`** — one file per domain table, barrel-exported from `index.ts`. Keeping schema separate from `src/` mirrors standard Drizzle project layout and keeps migrations independent of app code changes.
- **`src/app/(marketing)`** — route group for all public, SEO-indexable pages. Grouped so a shared "public" layout (navbar+footer) can wrap them without affecting dashboard routes.
- **`src/app/(auth)`** — route group for the few auth flows that need a real URL (email verification link, OTP entry, password reset) as opposed to the login/signup modal which is a global overlay component, not a route.
- **`src/app/(dashboard)`** — one shared authenticated shell layout, with role-specific subfolders (`author/`, `reader/`, `admin/`). Keeps role-gated logic co-located and makes it trivial to apply a single `permissions.ts` guard at the `(dashboard)/layout.tsx` level plus a second per-subfolder check.
- **`src/app/api/`** — Route Handlers for anything that needs a server endpoint: Auth.js catch-all, Stripe webhook (must be a raw Route Handler, not a Server Action, to verify the Stripe signature), and any mutation that benefits from a stable REST-ish endpoint (search, checkout creation).
- **`src/components/ui` vs `shared` vs feature folders** — `ui/` is the untouched-API shadcn primitives layer (Button, Dialog, Input) customized only via Tailwind theme tokens, never edited for one-off feature logic. `shared/` holds theme-specific composite components used across multiple features (Navbar, ArticleCard, AuthModal). Feature folders (`homepage/`, `article/`, `editor/`, `dashboard/`, `admin/`) hold components only that specific feature uses — this prevents `shared/` from becoming a dumping ground.
- **`src/lib/`** — all non-UI logic: DB client, auth config, Stripe/Resend clients, and critically `revenue-split.ts` which is the single place the 80/20 and 60/20/20 math (and the pooled-subscription distribution logic) lives, so it is never duplicated or drifted between the purchase flow and the subscription-period-distribution job.
- **`src/emails/`** — React Email components rendered server-side and handed to Resend; kept separate from `components/` because they render in an email client context, not the app's DOM/Tailwind runtime.
- **`src/styles/tokens.css`** — the literal CSS variables from `02_ThemeGuideline.md` Section 2, single source of truth wired into `tailwind.config.ts`'s `theme.extend.colors` so Tailwind utility classes (`bg-primary`, `text-muted`) map directly to the design tokens.

## Naming conventions

- **Files/folders:** kebab-case for all files and folders except Next.js reserved filenames (`page.tsx`, `layout.tsx`, `route.ts`, etc.) which keep their required casing.
- **Components:** PascalCase for the component name and its default export (`ArticleCard.tsx` exporting `ArticleCard`), file name matches component name exactly.
- **Hooks:** camelCase prefixed `use-` in filename (`use-auth-modal.ts`), exported function camelCase (`useAuthModal`).
- **Server actions / lib functions:** camelCase, verb-first (`createArticle`, `calculateRevenueSplit`, `grantSubscriptionAccess`).
- **Drizzle tables:** camelCase table variable name, plural snake_free (e.g. `export const articles = pgTable("articles", {...})`); DB column names snake_case via Drizzle's column mapping.
- **Route segments:** kebab-case (`publications/new`, `verify-otp`).
- **Env vars:** SCREAMING_SNAKE_CASE, documented in `.env.example` with a one-line comment per var.
